# 仕様書（試作版）と応募時の提示事項

依頼文「8．応募時にご提示いただきたい内容」①〜⑨の順に、**試作版で実装済みのこと**と**本番までに必要なこと**を分けて書きます。

## ① システム構成・開発方法・使用技術

```
[タブレット/PC のブラウザ] ──HTTPS──> [事業所サーバー or 閉域クラウド]
  static/ (HTML/CSS/JS)                 server.py（API・権限・操作ログ）
  音声入力(ブラウザ機能)                 app/ai.py（原案・確認事項）
                                        app/checks.py（請求前チェック）
                                        app/reports.py（分析・書類）
                                        SQLite（試作）→ PostgreSQL（本番想定）
```
- 試作版は Python 標準ライブラリのみ（追加パッケージなし）。導入・保守の手間を減らすため。
- 画面はアプリのインストール不要。タブレットのブラウザで動く。
- 開発方法：1事業所での実データ検証 → 不具合修正・操作性改善 → 展開、の段階型。

## ② ステップ①〜⑨への対応状況

| ステップ | 試作版 | 本番までに必要なこと |
|---|---|---|
| ① 登録・入力 | 実装済 | 既存の利用者・職員台帳（Excel/CSV）の取り込み機能、多言語表示（やさしい日本語・英語・ベトナム語等） |
| ② AI記録・申し送り | ルール型で実装済（推測しない） | 生成AIの導入有無の決定（下記③）、施設の記録様式に合わせた文型調整 |
| ③ DB・帳票連携 | 一元保存・検索・CSV出力 | **既存Excel様式（請求チェックシート・稼働表）の実物を受領し、セル位置への直接転記**を実装 |
| ④ 請求前チェック | 実装済（記録もれ・稼働矛盾・シフト/打刻・未承認・計画期限） | 加算・減算の算定ルール、国保連請求データ（請求ソフト側）との照合項目を確認して追加 |
| ⑤ 事故分析 | 実装済（類似検索・集計・会議資料） | 既存の紙の事故報告の取り込み |

| ⑦ チェック・通知 | 画面内通知 | メール・LINE WORKS等への通知（利用サービスの決定が必要） |
| ⑧ 承認・履歴 | 実装済（承認・差し戻し・全操作ログ） | 電子署名・タイムスタンプの要否確認 |
| ⑨ テスト・導入 | 自動テスト13件・画面確認済 | 実データ検証、職員説明会、手順書の改訂 |

## ③ 音声入力・AI記録作成・帳票連携の方法

**音声入力**：ブラウザの音声認識機能（Web Speech API）を使用。
注意：Chrome などでは音声認識がサーバー側で処理される場合があると MDN に記載があります
（MDN「Using the Web Speech API」https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API ）。
つまり**音声が端末外（ブラウザ提供元）へ送られる可能性がある**ため、本番では次のどちらかを選ぶ必要があります。
- A. 利用者名を話さない運用ルールで使う
- B. 事業所サーバー内で動く音声認識エンジンに差し替える（外部送信なし）

**AI記録作成**：試作版は「ルール型」。選んだ項目・定型文・メモだけを文章に並べ、
入力されていない事実は書かない。数値の異常（37.5℃以上など）・不足項目・注意語（転倒・誤薬・発熱など）を「確認事項」として出す。
生成AI（大規模言語モデル）を使う場合も、`app/ai.py` の `draft()` の入出力を変えずに差し替えられる構造です。
その場合は「学習に使われない契約・設定」「国内リージョン」「氏名の仮名化して送信」を条件にします（契約内容は採用サービスの規約で要確認）。

**帳票連携**：現在はExcelで開けるCSV（文字化けしないBOM付きUTF-8）。既存のExcel様式への直接書き込みは、実物の様式を受け取ってから実装します。

## ④ データベース・承認・履歴管理

- 全テーブルに `facility_id`（事業所ID）を持つ。
- 記録の状態：下書き → 承認待ち → 承認済み／差し戻し。承認後は職員が修正できない（管理者が直すと承認待ちに戻る）。
- `audit_log` に、ログイン・作成・修正・承認・差し戻し・CSV出力・打刻修正などを「だれが・いつ・変更前・変更後」で保存。画面から削除・編集する機能はない。
- 記録を削除するAPIはない（法定保存のため）。保存年数は `facilities.retention_years` に設定値として持つ。**年数は所管自治体の条例・基準で確認してから設定**してください。

この試作では提示していません。既存帳票の数、通知手段、生成AI・音声認識の方式（③のA/B）が決まると見積もれます。

## ⑦ 複数事業所への展開

- データは事業所IDで分かれており、ログインした職員は自分の事業所のデータしか見られない（全APIで `facility_id` を条件にしている）。
- 展開時に必要な追加：法人本部の横断閲覧権限、事業所ごとのチェック項目・必須記録の設定画面。

## ⑧ セキュリティ対策・保守

| 対策 | 試作版の実装 |
|---|---|
| アクセス権限 | 職員／サビ管／管理者の3段階。権限はサーバー側で毎回チェック |
| パスワード | PBKDF2-SHA256（12万回）で保存。平文で保存しない。5回失敗で5分ロック |
| セッション | HttpOnly・SameSite=Strict のクッキー、12時間で失効 |
| 改ざん対策 | POST には専用ヘッダー必須（CSRF対策）、画面はCSPで外部スクリプト禁止 |
| 通信暗号化 | `--cert/--key` で HTTPS（TLS1.2以上）。本番は必須 |
| 操作ログ | 全操作を記録（④） |
| 外部送信 | 記録データを外部AIへ送る処理はない（音声入力のみ③の注意あり） |

本番で追加：データベースの暗号化とバックアップ（自動・別拠点）、端末紛失時の対策（MDM）、二要素認証、定期的な脆弱性確認。
厚生労働省「医療情報システムの安全管理に関するガイドライン」等、参照すべき指針は導入時に事業所と確認します。
